# keystone-ideas 기준서

사용자가 현재 작업 밖의 고려사항·기능 후보를 필요했던 이유와 함께 보관하고 자연어로
관리하도록 한다. 아이디어는 제안·기억이며 정책·작업 약속·실행 승인이 아니다.

## 저장과 식별

1. Project document root는 STD-KEYSTONE-010을 따른다. 충돌이 없으면 최초 등록 시에만
   `ideas/key-ideas.md`를 만든다. 아이디어 등록만을 위해 Keystone 초기화나 Round를 요구하지 않는다.
2. 기본 파일과 `ideas/key-ideas-{topic}.md`의 flat 파일 집합이 한 번호 공간이다.
   기본 필드는 `## IDEA-001 · 제목`, `- 필요했던 이유: ...`, `- 기록일: YYYY-MM-DD`다.
   아이디어 항목만 `##` heading을 사용하고 추가 내용의 heading은 `###` 이하로 둔다.
   선택 내용은 그 아래 자유 본문에 두며 가급적 300자 이내로 정리하되 자동 절단하지 않는다.
3. ID는 현재 파일 집합에 남은 최댓값+1이며 없으면 001이다. 최소 세 자리로 표시하고 999를
   넘으면 자릿수를 늘린다. 중간 빈 번호를 채우지 않으며 마지막 삭제 번호는 재사용할 수 있다.
   과거 최대 번호·삭제 이력·휴지통을 저장하지 않는다.
4. 수정·이동 시 ID와 최초 기록일을 유지한다. 날짜는 사용자의 현지 날짜를 기본으로 하며
   사용자가 명시한 실제 기록일은 존중한다. 수정일·승인·우선순위·태그·상태 필드는 필수가 아니다.
5. 노트 파일은 비규범적 메모로서 frontmatter·keymeta·graph node·색인이 필요하지 않다.
   재사용 가능한 IDEA 번호를 stable graph ID로 쓰지 않는다. 작업서가 아이디어를 근거로 삼으면
   필요한 맥락을 작업서에 보존하고 제목·기록일을 함께 식별하여 번호 재사용으로 의미가 바뀌지 않게 한다.
6. 내용이 늘어도 자동 분할하지 않는다. 반복 주제와 불필요한 읽기 비용을 근거로 분할을 제안하고,
   허용된 정리 범위 안에서만 이동한다. 이동 전후 ID·기록일·본문을 대조하고 빈 주제 파일은 만들지 않는다.

## CRUD와 사용자 안내

1. 자연어에서 의도를 판별한다. 의견·조회는 read-only이며 명시적인 등록·수정·삭제 요청만 쓰기다.
   뜻이나 대상이 모호하면 한 번에 하나의 질문만 한다. 명확한 요청에 재승인을 요구하지 않는다.
2. 등록 전 관련 표현으로 유사 후보를 찾고 본문을 확인한다. 실제로 비슷한 후보가 있으면 모두
   공통 표로 보여주고 기존 항목 추가 또는 별도 등록을 묻는다. 답변 전에는 쓰지 않는다.
   사용자가 같은 후보를 이미 검토하고 별도 등록을 선택했다면 같은 질문을 반복하지 않는다.
3. 검색·조회·상세·유사 후보·수정/삭제 대상·모든 CRUD 결과는 아래 열과 순서의 표를 사용한다.

   | ID | 제목 | 필요했던 이유 | 기록일 |
   |---|---|---|---|

   단건도 표이며 빈 결과는 같은 헤더와 결과 없음 안내를 사용한다. 긴 제목·이유는 표시만
   요약한다. 추가 내용·위치·관련성·확인 질문·처리 결과는 표 아래에 둔다. 삭제 후에는 삭제
   직전 항목 표와 삭제 성공 안내를 보여준다. 실패·미응답 상태를 성공으로 표시하지 않는다.
4. 실제 저장에서 지정 항목만 수정·제거한다. 최신 내용과 읽은 바이트를 쓰기 직전 대조하고
   변경됐으면 다시 읽는다. 동시 변경으로 의미가 달라졌다면 멈추고 재확인한다.
   생성 직전 모든 노트 파일의 번호를 다시 확인한다. 이 재확인은 원자적인 다중 writer 잠금이
   아니므로 동시 쓰기가 감지되면 중단한다. 사용자 편집을 덮어쓰거나 자동 재번호화하지 않는다.
5. 삭제 요청은 실제 제거다. 오래됐거나 비슷하다는 이유로 임의 삭제·병합하지 않는다.
   쓰기 후 다시 조회하여 의도한 결과와 무관한 내용 보존, 중복 ID 부재를 확인한다.

## 검색과 비용

1. ID는 exact lookup한다. 자연어는 대상·목적 중심의 소수 검색어로 제목·이유·추가 내용을 찾는다.
2. 후보 본문을 읽고 관련성을 판단한다. 부족하면 유사 표현·외래어·사용 목적을 확장한다.
   예: 엑셀 → CSV/내보내기/다운로드. 단어 일치만으로 동일 아이디어라고 판단하지 않는다.
3. 두 차례 검색 뒤에도 불충분하면 작은 저장소(기본 50개 이하)는 제목 표를 검토하고 필요한
   본문만 읽는다. 큰 저장소는 관련 주제나 사용자의 구체적인 단서로 좁힌다. 사용자의 전체
   조회 요청은 20행 단위로 나누어 처리할 수 있다. 이는 조절 가능한 탐색 기본값이며 성능 한계가 아니다.
4. 부분 검색으로 부재·중복 없음·의미 검색 완전성을 주장하지 않는다. 읽기 실패·잘못된 형식·
   중복 ID는 결과 없음과 구분한다. helper는 notes 범위만 읽고 캐시·인덱스·상태 파일을 쓰지 않는다.
5. helper의 전체 파일 읽기량과 선택된 항목/본문 출력량을 구분한다. 현재 구현은 선형 파일
   scan이며 bounded 출력만으로 I/O 비용이 줄었다고 보고하지 않는다.

## 기존 스킬과 검증

Ideas는 노트 CRUD만 소유하며 Author의 일반 source 편집 권한을 대체하지 않는다.
Reader는 선택한 작업의 관련 노트를 read-only로 찾고 같은 표로 안내한다. 초기 세션에서 전체
노트를 읽거나 노트 부재를 준비 실패로 다루지 않는다. Author는 명시적 작업 구체화 요청만
받아 정책·범위·완료 조건을 만든다. 노트 등록은 Work State·graph·Round 전이를 유발하지 않는다.

검증은 최초 생성, 사용자 표현 변형, 유사 후보 질문과 무응답 no-write, 모호한 삭제,
날짜·다른 항목 보존, 중간/끝/전체 삭제 이후 번호, 분할 후 조회, malformed/duplicate 입력,
표의 특수문자와 빈 결과를 포함한다. 임시 소비 프로젝트와 합성 규모 실험을 사용하며
정적 검사·기계적 검색·실제 AI 관련성 판단 결과를 분리하여 기록한다.
