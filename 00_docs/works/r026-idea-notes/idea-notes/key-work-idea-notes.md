# 아이디어 노트 청사진·작업서

## Goal

현재 작업 밖의 고려사항과 기능 후보를 "왜 필요했는지" 기억할 수 있는 짧은 기록으로 남긴다.
사용자는 자연어로 등록·조회·수정·삭제하고, AI는 일정한 탐색 절차 안에서 표현과 관련성을
판단한다. 기록을 위해 Round·작업서·복잡한 상태 관리나 DB 운영을 요구하지 않는다.

## 사용자 방향과 설계 경계

1. 제품 명칭은 아이디어 노트, 신규 스킬 이름은 `keystone-ideas`다.
2. 파일 기반으로 시작한다. 최소 기록 형식과 검색 절차를 고정하고 요약·검색어 확장은 AI에 맡긴다.
3. 등록은 구현 약속·기준서 변경·실행 승인이 아니다. 확정된 정책은 기존 기준서·결정 기록이
   소유하며 노트는 필요할 때 그 근거를 연결한다.
4. 한 파일로 시작하고 실제 탐색 부담과 반복 주제가 생겼을 때 주제별로 분리한다.
   항목별 파일, 필수 태그·우선순위·공수·일정·승인 상태는 초기 요구가 아니다.
5. 최초 청사진을 바탕으로 S01에서 기준을 정합화하고 S02~S03 구현·검증을 완료했다.
   현행 계약은 Project STD-KEYSTONE-064와 Ideas 기준서에서 복구한다.

## 저장 구조와 최소 기록

설정된 document root 아래 `ideas/key-ideas.md`를 최초 등록 시 필요할 때 생성한다.
기본 root에서의 예시는 `00_docs/ideas/key-ideas.md`다. 특정 Round에 종속시키지 않는다.
빈 주제 파일이나 수동 중복 색인은 기본 생성하지 않는다.

```markdown
## IDEA-001 · 검색 결과 CSV 다운로드

- 필요했던 이유: 운영자가 검색 결과를 엑셀에서 가공할 필요가 있어 제안했다.
- 기록일: 2026-10-12

현재 검색 개선 범위에서는 제외했다. 관리자 검색이나 내보내기를 개발할 때 다시 검토하면 좋겠다.
관련: R025
```

위 예시는 형식 설명이며 실제 등록된 아이디어가 아니다.

- 기본: 저장 위치와 무관한 고정 ID, 구체적인 제목, 필요했던 이유를 담은 짧은 본문, 기록일.
- 신규 ID는 ideas 영역의 모든 파일에 현재 남아 있는 ID 번호 중 최댓값에 1을 더해 부여한다.
  항목이 없으면 `IDEA-001`부터 시작하며 중간의 빈 번호는 채우지 않는다.
  예: `001, 003`이 남아 있으면 다음은 `004`, 마지막 `003`을 삭제해 `001, 002`만
  남아 있으면 다음은 다시 `003`이다. 삭제 이력이나 과거 최대 번호를 별도 보존하지 않는다.
  고정 ID는 항목이 존재하는 동안 수정·이동해도 유지한다는 뜻이며, 삭제 이후의 영구 미재사용을 뜻하지 않는다.
- 기록일은 최초 등록 날짜를 `YYYY-MM-DD`로 저장하며 수정·파일 이동 시에도 유지한다.
  수정일·변경 이력은 기본 필드로 추가하지 않는다.
- 선택: 상황에 따라 아이디어의 구체적인 내용이나 설명을 짧게 추가할 수 있다. 추가 내용은
  가급적 300자 이내로 기록하되 맥락 보존에 필요하면 예외를 허용하며, 강제 제한이나 자동 절단을 하지 않는다.
  보류 이유, 다시 볼 조건, 관련 Round·문서도 추가할 수 있다. 사용자가 제공하지 않은 사실을 만들지 않는다.
- 고려사항·구현 후보는 본문에서 의미를 구분할 수 있으면 충분하다. 분류 필드를 강제하지 않는다.
- 아이디어는 제안·기억 기록이다. `key-` 파일에 있다는 이유로 정책 또는 구현 요구로 승격하지 않는다.
- 분할 시 `ideas/key-ideas-{topic}.md`로 관련 묶음만 이동하고 ID·맥락을 보존한다.
  미분류 항목은 기본 파일에 남긴다. 날짜별·항목별 분할과 자동 대규모 재분류를 기본 동작으로 삼지 않는다.
- `30~50개 또는 수백 줄`은 분리 검토의 초기 참고치이며 성능 한계나 자동 분할 조건이 아니다.
  무관한 본문을 반복해서 읽는 비용과 자연스러운 주제 묶음의 존재로 판단한다.

## CRUD와 검색 계약

### 자연어 요청과 공통 출력

스킬 이름은 `keystone-ideas`이며 뒤에 오는 자연어로 생성·조회·수정·삭제 의도를 판단한다.
조회·의견 요청을 쓰기 요청으로 추론하지 않으며 의도나 대상이 모호하면 필요한 질문만 한다.

아이디어를 제시하는 모든 CRUD 화면은 개수·용도와 무관하게 아래 열과 순서의 표를 사용한다.
일반 검색·상세 조회, 등록 전 유사 후보, 수정·삭제 대상 확인과 각 작업의 처리 결과에
같은 형식을 적용한다. 한 건도 표로 보여주며 목록을 문장이나 bullet로 대체하지 않는다.

| ID | 제목 | 필요했던 이유 | 기록일 |
|---|---|---|---|
| IDEA-001 | 검색 결과 CSV 다운로드 | 운영자가 결과를 엑셀에서 가공해야 함 | 2026-10-12 |

위 표는 출력 예시다. 제목·이유가 길면 표시만 요약하고 원문을 보존한다.
추가 내용·관련 링크가 필요한 상세 조회는 기본 표 아래에 해당 ID와 함께 제공한다.
관련성 설명, 확인 질문, 등록·수정·삭제 성공 여부도 표 아래에서 짧게 안내한다.
삭제 성공 시 삭제 직전 항목을 같은 표로 보여주고 삭제됐음을 명시하며, 실패를 성공으로 표시하지 않는다.
결과가 없으면 헤더와 구분선만 있는 같은 표와 결과 없음 안내를 사용하고 가짜 아이디어 행을 만들지 않는다.

### 생성

명시적 기록 요청을 짧은 제목·배경으로 정리한다. 관련 표현으로 기존 후보를 찾아 중복 가능성을
확인하되 비슷하다는 이유만으로 기존 항목에 자동 병합하지 않는다. 검색이 제한적이면 중복이
전혀 없다고 보장하지 않는다. 유사 후보가 있으면 조회와 같은 표로 후보들을 먼저 보여주고
기존 항목에 추가할지, 별도로 등록할지 질문한다. 답을 받기 전에는 등록·수정하지 않는다.
사용자가 설명한 차이를 반영하고 기존 항목 선택이 모호할 때만 대상을 확인한다.
유사 후보가 없고 등록 의도가 명확하면 별도 재확인 없이 기록하고 공통 표로 결과를 안내한다.

### 조회

1. ID가 있으면 ideas 범위에서 정확한 항목을 찾는다. 위치가 달라져도 ID는 유지한다.
2. 자연어 요청에서는 대상·목적·관련 표현을 뽑아 제목과 본문을 검색한다.
3. 후보 본문을 읽고 관련성을 판단하여 공통 표로 제시한다. 필요한 위치·관련성 설명은 표 아래에 둔다.
4. 후보가 없거나 부족하면 유사 표현으로 탐색을 넓힌다. 작은 저장소는 전체 읽기를 허용하지만
   매 요청마다 전체 본문을 읽는 것을 기본으로 삼지 않는다.
5. 큰 저장소에서 전부 읽지 못하면 확인한 범위와 한계를 알린다. 부분 검색 실패를 존재하지
   않는다는 증거로 삼지 않는다. 전체 목록도 공통 표를 사용하며 필요하면 같은 열로 나누어 보여준다.

예: "엑셀로 뽑는 아이디어" → `엑셀`, `CSV`, `내보내기`, `다운로드` 후보를 찾은 뒤 본문 확인.
문자열 일치만으로 의미가 같다고 확정하거나 DB·임베딩 없는 의미 검색의 완전성을 주장하지 않는다.

### 수정·삭제

ID 또는 문맥으로 하나의 대상을 특정하고 최신 본문을 확인한 뒤 요청한 범위만 변경한다.
대상이 여러 개면 한 번에 하나의 질문으로 확인한다. 조회·의견 요청은 수정 권한이 아니다.
수정 시 ID와 여전히 유효한 배경을 보존하며, 삭제는 명시적으로 지정된 항목에 한정한다.
삭제는 저장 문서에서 해당 항목을 실제 제거하는 동작이다. 별도 휴지통·보관 상태·복구 기능을
만들지 않는다. 신규 ID 부여는 현재 남은 번호의 최댓값을 기준으로 하므로 마지막 번호 삭제 후에는
그 번호가 다시 부여될 수 있다.
오래됐거나 유사하다는 이유로 자동 삭제·병합하지 않는다. 관련 없는 항목과 사용자 편집을 보존한다.

## 스킬 책임과 기존 흐름 연결

- `keystone-ideas`: 아이디어 영역 CRUD와 그에 필요한 제한적 탐색을 소유한다.
  등록만을 위해 Author 호출, Round 생성, Work State 또는 전체 graph 검증을 요구하지 않는다.
- Reader: 사용자가 선택한 작업을 준비할 때 관련 노트를 제한적으로 찾아 고려사항으로 제시한다.
  매 세션 전체 읽기나 노트 자동 수정은 하지 않는다. 아이디어가 없어도 준비를 계속한다.
- Author: 명시적 작업 구체화 요청에서 아이디어를 근거로 Round·작업서를 작성한다.
  기존 생성과 실행의 분리는 유지한다. 작업으로 연결됐다는 사실은 구현 완료가 아니다.
- 기존 `key-` source 작성의 Author 소유권과 신규 Ideas의 제한된 소유권을 S01에서 명시적으로
  정합화한다. 일반 기준서·작업서 편집 권한을 Ideas에 확대하지 않는다.
- 사용자가 해당 기능을 사용하기 전 빈 저장소를 의무 생성하지 않는다. 설치된 스킬은 소비
  프로젝트에 이 구현 저장소의 개발 기준서가 없어도 사용할 수 있어야 한다.

## Scope

Include:

- 위 저장·기록·검색·CRUD 계약과 최소 metadata·ID 규칙 정의
- 프로젝트 및 관련 스킬 기준 정합화, 신규 Ideas 기준과 스킬 source
- 필요한 Reader·Author 안내, repository 내 패키징·스킬 목록 연결과 focused 검증
- 모호한 대상·유사 표현·중복 후보·파일 이동·ID 충돌·기존 편집 보존 시나리오
- 규모별 검색 품질과 읽기·변경 비용 관찰, 한계 및 후속 개선 판단 근거

Exclude:

- NoSQL·외부 DB·벡터 검색·임베딩 서비스·상시 실행 서버·필수 파생 검색 인덱스
- 칸반·우선순위 계산·일정·공수·담당자·복잡한 아이디어 상태와 수락 workflow
- 기존 대화·완료 Round를 전수 수집하여 아이디어로 자동 이전
- 실제 제품 기능 구현, 다른 Round 범위·상태 변경, 소비 프로젝트 일괄 migration
- 전역 설치·publish, 별도 승인 없는 삭제·병합·대량 재분류

## 구현에서 확정한 세부사항

1. 현재 최댓값+1은 모든 flat 노트 파일을 읽어 계산한다. 생성 직전에 다시 읽고 중복·malformed
   입력은 중단한다. 삭제 이력 registry를 만들지 않는다.
2. 노트는 frontmatter·키메타가 없는 메모다. `##` 항목과 이유·기록일 필드만 고정하고
   세부 내용은 자유 본문에 둔다. IDEA 번호는 영구 graph 관계 키로 사용하지 않는다.
3. 작은 읽기 전용 helper가 파싱·literal 검색·ID 계산·표 출력을 담당한다. AI가 최신 바이트를
   대조하고 요청된 부분만 직접 편집한다. 원자적인 다중 writer 잠금은 제공하지 않는다.
4. 작업 링크는 선택 본문이며 닫기·보관 상태를 만들지 않는다. 작업서에는 필요한 맥락을 보존한다.
5. 검색 2회 후 작은 저장소(기본 50개 이하)는 제목 표를 살피고 필요한 본문만 읽는다.
   큰 저장소는 주제·단서로 좁힌다. 출력 기본 20행, 최대 200행/page이며 남은 결과를 알린다.
   이것은 조절 가능한 탐색 기본값이지 성능 한계나 사용자에게 요구하는 새 정책이 아니다.

## Step 계획

### R026/S01 — 기록·탐색 계약과 기준 정합화

- **Goal:** 가벼운 노트 모델과 스킬 권한·검색 절차를 구현 가능한 계약으로 만든다.
- **Scope:** 청사진의 세부사항, Author 소유권과의 경계, ID·분할·쓰기 충돌 처리,
  관련 기준과 검증 사례를 구체화한다.
- **Source Context:** 사용자 대화 방향, 위 Source Context와 현재 accepted 기준.
- **Completion Criteria:** 최소 형식, 저장 경계, CRUD·조회 중단 규칙과 검증 기대값이 명확하다.
  Production 구현 전에 필요한 기준 정합화를 수락받거나 충분한 기존 기준의 no_change 근거가 있다.
- **Stop Conditions:** 사용자 의도·권한 변경이 미해결이거나 필수 DB·상태 체계 등 범위 확대가 필요하다.
- **Verification:** 실제 사용자 사례가 가능하면 사용하고, 합성 사례는 구분하여 10~20개 노트와
  다른 표현의 질의·모호한 대상·부재 사례에 계약을 대입한다. 알려진 관련 항목과 금지 변경을 정한다.
- **Expected Output:** 정합화된 기준, 최소 저장·ID 규칙, 검증 사례와 S02 대상 파일 목록.

### R026/S02 — 아이디어 스킬 구현과 연결

- **Goal:** 자연어 CRUD와 단계적 검색을 수행하는 독립 스킬을 제공한다.
- **Scope:** Ideas skill과 필요한 최소 지원 파일, Reader·Author 연결 및 확인된 패키징 경로.
  Helper는 반복 정확성 문제를 해결하는 경우에만 추가한다.
- **Source Context:** 수락된 S01 계약, 실제 skill package 구조·설치와 검증 관례.
- **Completion Criteria:** 네 작업이 요청 범위에서 동작하고 초기 저장소 부재·ID 충돌·모호성에
  안전하게 대응한다. 설치 패키지에 필요한 파일이 포함되고 다른 스킬의 내부 runtime import를 요구하지 않는다.
- **Stop Conditions:** 미승인 runtime/schema 변경, 외부 dependency 또는 기존 작업 일괄 이전이 필요하다.
- **Verification:** 임시 소비 프로젝트에서 생성→검색→수정→삭제, 관련 없는 항목 보존과
  분할 후 ID 탐색, 중간 삭제 후 빈 번호 미사용, 마지막 번호 삭제 후 재부여,
  전체 삭제 후 `IDEA-001` 시작을 확인한다. 구현한 helper와 계약 경계만 focused 검증한다.
- **Expected Output:** 신규 스킬과 최소 연결, 검증 결과 및 한계.

### R026/S03 — 검색 품질·관리 비용 검증

- **Goal:** 가벼운 사용성과 검색 정확성, 기준·구현 일치를 검증한다.
- **Scope:** S01 사례, 규모 증가와 주제 혼합, 단계적 검색과 전체 읽기의 비용 비교.
- **Source Context:** S01 기대값, S02 구현, 동일한 fixture·질의·실행 조건.
- **Completion Criteria:** ID 조회와 CRUD에서 대상을 오인하거나 무관한 항목을 변경하지 않는다.
  알려진 관련 항목의 검색 누락·불필요 후보·추가 질의와 읽은 파일/분량을 기록한다.
  누락과 불확실성을 숨기지 않으며 품질 문제가 남으면 완료로 주장하지 않고 해결 또는 한계 수용을 구한다.
- **Stop Conditions:** 배경 소실·잘못된 수정/삭제·중복 ID·등록의 실행 승인 오인이 남거나
  미측정 성능을 근거로 자동 분할·새 저장소를 도입해야 한다.
- **Verification:** 우선 10~20개 사례를 확인하고 50·200개 등 합성 묶음으로 탐색 비용을 비교한다.
  개수는 실험 규모이며 한계치가 아니다. 표현 변형·중복 후보·파일 이동·검색 부재를 포함한다.
  정적 계약 검사와 실제 에이전트 검색 관찰을 구분하고 전자만으로 자연어 검색 품질을 입증하지 않는다.
  필요한 package 검사와 affected 문서 정합성을 확인하며 전역 설치는 수행하지 않는다.
- **Expected Output:** 검색·변경 정확성, 규모별 관찰, 분할 권고 근거와 잔여 한계.
